# AtlasDocs v0.7 Product Experience and Entity Lifecycle Roadmap

## Status

Proposed roadmap for the next public AtlasDocs implementation sprint.

Read `docs/product-experience-spec.md` as the product direction and preserve the existing Paperless boundary.

## Sprint goal

Make AtlasDocs feel like an entity-centered semantic application rather than a document queue with semantic fields.

The sprint should establish the lifecycle and navigation foundations without implementing the complete future knowledge graph.

## Scope

### 1. Home and navigation

- Home with global search entry point.
- Primary navigation: Home, Explore, Classify, Ingest.
- Move Reconcile and Disconnect into administration/profile.
- Preserve operational queues separately from knowledge exploration.

### 2. Explore and canonical cards

- Documents and Knowledge categories.
- Entity-oriented search result contract.
- Canonical cards for Document, Person, Organization, Country, Case, and Concept.
- Document grid/list with thumbnails, sorting, filters, and pagination.
- Reuse cards in search and relationship selection.

### 3. Inline document experience

- Inline Preview.
- Download through the authenticated BFF.
- Open original in Paperless as a secondary action.
- Technical metadata, OCR, history, and versions under progressive disclosure.

### 4. Entity pages

- Basic entity detail pages.
- Related entities grouped by type.
- Related documents.
- Relationships, backlinks, provenance, and semantic completeness.
- No graph visualization yet.

### 5. Lifecycle categories

Add explicit lifecycle category support:

```text
Evidence
Master Data
Organizational
```

The category must affect permitted operations and UI actions.

### 6. Evidence lifecycle

Implement or complete:

- create;
- replace;
- move to Paperless trash;
- restore;
- permanent delete;
- tombstone state;
- replacement history.

Replacement must preserve the Atlas entity UUID and relationships. New real-world documents must create new entities.

### 7. Master Data safeguards

Implement safeguards for Master Data:

- rename;
- archive;
- restore;
- merge/redirect design;
- prevent destructive deletion while relationships exist.

If full merge is too large for this sprint, implement the data-model/API contract and a safe placeholder rather than a misleading delete operation.

### 8. Paperless lifecycle reconciliation

Use collection-level reconciliation for active, trashed, and purged Paperless documents. Preserve tombstones and avoid leaking unavailable metadata.

### 9. Semantic completeness

Calculate completeness during creation and mutation, not only in the viewer.

Initial states:

```text
empty | partial | classified | needs_review
```

Keep rules small and explainable. Do not build a generic ontology-rules editor yet.

## Recommended implementation order

1. Establish lifecycle category and state contracts.
2. Add safe entity/search/card APIs.
3. Add document and entity Explore UI.
4. Add lifecycle-aware document actions.
5. Add Master Data archive/merge safeguards.
6. Add collection reconciliation.
7. Add browser, authorization, and destructive-operation tests.
8. Update public documentation.

## Tests required before merge

- Evidence, Master Data, and Organizational lifecycle rules.
- Move to trash, restore, and permanent delete authorization.
- Tombstone visibility and no metadata leakage.
- Replacement preserves entity UUID and relationships.
- Failed replacement leaves the old reference intact.
- New logical document creates a new entity.
- Merge/redirect preserves or migrates relationships safely.
- Explore entity results and canonical card rendering.
- Preview/download authorization.
- Collection reconciliation with active, trashed, and purged documents.
- Semantic completeness on create, relationship add, relationship removal, replace, archive, and restore.
- Mobile, keyboard, loading, empty, error, and destructive-confirmation states.

## Explicitly defer

Do not include these in v0.7 unless already required by the contracts:

- global graph viewer;
- full Perspectives system;
- timeline engine;
- Evidence entity model beyond the lifecycle foundation;
- LLMs;
- MCP;
- embeddings/vector search;
- Supernova;
- complex multi-user workspace ACLs;
- full ontology editor.

## Acceptance criteria

1. AtlasDocs has a clear Home, Explore, Classify, and Ingest product structure.
2. Explore uses canonical entity cards and returns semantic entities.
3. Documents remain evidence while Paperless remains document authority.
4. Lifecycle category controls permitted operations.
5. Evidence replacement preserves Atlas identity and relationships.
6. New real-world documents create new Atlas entities.
7. Paperless trash and purge states reconcile safely.
8. Master Data cannot be casually deleted while relationships exist.
9. Semantic completeness is assigned and recalculated during creation and mutation.
10. No inaccessible Paperless metadata leaks through navigation, search, counts, or relationships.
11. Full backend, frontend, browser, migration, and Docker tests pass.
12. Documentation accurately describes current behavior versus future vision.

## Integration note: Paperless download variants

The document experience must preserve Paperless version-aware file actions through the AtlasDocs BFF.

```text
/api/documents/{paperless_id}/download/?original=true&version={version_id}
/api/documents/{paperless_id}/download/?version={version_id}
```

The first requests the original source representation for a selected Paperless version. The second requests the selected Paperless version representation. `version_id` is owned by Paperless and must never be confused with an AtlasDocs UUID.

Add API and browser tests for both actions. Do not expose direct authenticated Paperless URLs or tokens to the browser.
