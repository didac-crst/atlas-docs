# AtlasDocs v0.2 UI Design Proposal

## Product intent

AtlasDocs is a semantic classification layer beside Paperless-ngx: Paperless owns the document; AtlasDocs records typed meaning.

## Primary user goal

Classify a document quickly: pick an unclassified Paperless document, attach a seeded relationship, confirm it stuck, optionally open the authoritative Paperless viewer.

## Visual direction

Calm archival workbench, not a dashboard. Editorial typography, restrained ink-on-paper palette, clear separation between Paperless authority and AtlasDocs semantics. No card grids, metric strips, or sidebar chrome.

## Primary visual element

The selected document’s classification decision: relationship type + target, with current confirmed relationships immediately adjacent.

## Immediate context

Paperless title, document id, and an `Open in Paperless` action. Current AtlasDocs relationships with origin and status.

## Supporting information

Needs-classification queue (list of Paperless documents lacking confirmed relationships). Seeded relationship types and allowed concept targets.

## Technical / advanced detail

Raw ids, API errors, duplicate conflicts. Progressive disclosure only when something fails.

## Interaction model

Single document-workbench:

1. **Needs classification** list (left / top on mobile).
2. Selecting a row opens **document detail** in the same workspace (desktop split; mobile replaces list with detail + back).
3. **Classify** form: choose relationship type, then target concept filtered by that type; submit; show success or error inline.
4. Optional remove of an existing relationship from the detail list.

No batch mode, no graph, no ontology editor.

## Screen hierarchy and navigation

```text
/ui                         → Needs classification workbench
/ui/documents/{paperless_id} → Same workbench with that document selected
```

Server-rendered pages from the existing FastAPI app (Jinja2 + CSS + small progressive JS). No separate SPA framework unless this model proves insufficient.

## How Paperless vs AtlasDocs are distinguished

| Region | Source | Presentation |
| --- | --- | --- |
| Title, id, Open in Paperless | Paperless | Labeled “Paperless”; secondary text; external link |
| Relationships, classify form | AtlasDocs | Labeled “AtlasDocs”; primary action surface; origin/status shown as text, not color alone |

## States

| State | Behavior |
| --- | --- |
| Loading | Queue and detail show quiet placeholders; controls disabled |
| Empty queue | “Nothing needs classification” with short explanation |
| Empty detail | Prompt to select a document from the queue |
| Selected | Detail populated; classify form focused |
| Success | Inline confirmation; relationship appears in list; item may leave queue if it now has a confirmed relationship |
| Error | Inline message for 400/409/404/502; form remains editable |
| Auth denial | Document treated as not found; no semantic leakage |

## Keyboard and mobile

- List and form fully keyboard operable; visible focus rings.
- Enter submits classify; Escape returns mobile detail → list.
- Touch targets ≥ 44px; long titles wrap/truncate with title attribute.
- Mobile: list-first; detail is a full-width second step, not a squeezed two-column layout.

## Clarifications (required)

### UI authentication

Do not silently use `PAPERLESS_TOKEN` for browser users. The workbench collects a Paperless token once via `POST /ui/connect`, stores it **server-side**, and sets an opaque random session ID in an HttpOnly cookie (`SameSite=Lax`, `Secure` configurable for HTTP development / required for HTTPS production). The Paperless token never appears in cookies, HTML, or JavaScript.

JSON API document endpoints require an incoming `Authorization` header on every request (401 if missing). No service-token fallback for document access.

Production (`ATLASDOCS_ENV=production`) requires a non-default `SESSION_SECRET`, `SESSION_SECURE=true`, and a non-default `DATABASE_PASSWORD`. `ATLASDOCS_ENV` itself is mandatory and must be set explicitly. Sessions expire explicitly and logout deletes the server-side record.

### Unclassified pagination

`GET /documents?unclassified=true` fetches **one** Paperless page (`page_size=25` by default and max), then runs a **single** AtlasDocs query for confirmed `paperless_document_id`s in that page. It returns the subset without confirmed relationships. No per-document Paperless round-trips and no unbounded scan.

### Mutations

Browser mutations use `POST` forms with CSRF tokens tied to the session. JSON API may use `DELETE /relationships/{id}` with `Authorization`. Never mutate via `GET`.

## API additions (minimal)

Existing:

- `GET /documents/{id}`
- `POST /documents/{id}/relationships`

Add:

- `GET /documents?unclassified=true&page=1&page_size=25` — one Paperless page, filtered to docs with no confirmed AtlasDocs relationships.
- `GET /documents/{id}` — extend payload with Paperless metadata (`title`, `open_url`) and relationship `id`.
- `DELETE /relationships/{id}` — remove one relationship after Paperless access check on its document.
- `GET /relationship-types` — seeded types with target ontology.
- `GET /ontologies/{code}/concepts` — concepts for classify targets.

Paperless access only through the REST client. No Paperless DB. API container contract (image/cmd/env) unchanged; UI served from the same app. Do not publish host port 3041 in generic Compose.

## Stack choice

Stay on FastAPI: Jinja2 templates + one CSS design-token file + minimal JS for form feedback. Avoid React/Vue for v0.2.

## Validation plan

API tests: auth denial → 404; empty unclassified list; create relationship; duplicate 409; Paperless 5xx/timeout → 502; delete relationship.

UI checks: desktop split and mobile list→detail; keyboard tab order; focus visible; long titles; loading/empty/error/success.

## Trade-offs

- Unclassified list depends on Paperless document listing + per-doc or set-based AtlasDocs checks; keep page size small for v0.2.
- Server-rendered UI is less flashy than an SPA but matches “smallest useful” and existing Python stack.
- Relationship delete by id requires exposing ids in API responses (additive, non-breaking for current clients that ignore unknown fields if any; response shape grows intentionally).
