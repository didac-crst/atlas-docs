# AtlasDocs v0.6 Explore and Semantic Workbench

## Status

Active sprint specification for the public AtlasDocs repository.

Read together with the [v0.5 ingestion specification](v0.5-ingestion-classification-spec.md), [ADR 0002](adr/0002-v05-session-ingest-security.md), the UI/UX design specification, the AtlasDocs brand direction, and `docs/semantic-navigation-spec.md` (future direction; may not exist yet in-repo).

Update [roadmap.md](roadmap.md) as phases land.

## Product direction

AtlasDocs should become the primary semantic work and exploration interface.

Paperless remains authoritative for original files, OCR, previews, downloads, permissions, and document lifecycle.

AtlasDocs owns ingestion experience, semantic entities, relationships, concepts, classification, exploration, and contextual document understanding.

```text
Paperless: stores, OCRs, authorizes, serves originals
AtlasDocs: ingests through Paperless, browses, classifies, relates, explores
```

AtlasDocs must not become a Paperless database replacement or duplicate the complete Paperless viewer.

## Product modes

### Explore

Answers: “What exists, and what is related to it?” Explore is calm, browsable, and discovery-oriented.

### Classify

Answers: “What needs work?” Classify remains a dense workbench with selection, bulk operations, and semantic completeness states.

These modes must not become duplicate screens.

## Required corrections

### Document title propagation

Never put `atlasdocs:<uuid>` into the user-facing Paperless title.

```text
User title supplied -> send that title to Paperless
No user title supplied -> omit the title field and let Paperless derive its normal title
```

The AtlasDocs UUID belongs in the Atlas entity, external reference, and technical details only.

Task response document IDs remain the primary ingestion resolution mechanism. Any fallback must use a supported Paperless field and an exact unique match. Never guess by filename, timing, or fuzzy title matching. If title-less resolution cannot be deterministic, keep the job retryable and report the limitation.

### Inline preview

Document detail should open Preview inline by default.

```text
Document title and metadata
[ Preview ] [ Download ] [ Add relationship ] [ Open original in Paperless ]
--------------------------------------------------------------------------
| inline PDF/image preview                 | relationships and context    |
```

Use the existing authenticated server-side BFF. Support PDF and safe raster images initially. Keep Paperless tokens server-side. Offer “Open preview in new tab”. Keep “Open original in Paperless” as a secondary action. Do not recreate the full Paperless viewer. Preserve authorization and `Cache-Control: no-store`.

## Navigation and home

Primary navigation becomes:

```text
Home | Explore | Classify | Ingest
```

Reconcile, connection management, and Disconnect move into profile/settings/administration. Keep the capabilities, but remove them from primary product navigation.

Home becomes a launcher with global search, Explore, Needs classification, Needs review, Failed ingestion, reconciliation issues, recently added documents, and recently changed entities or relationships. Counts must respect Paperless authorization.

## Explore

Implement Explore as a document and entity browsing surface, not a Paperless clone and not a graph viewer.

Initial modes:

```text
All | Documents | People | Organizations | Countries | Cases | Concepts
```

Documents may be the first fully implemented result type, but the API must be entity-oriented.

Support free-text search, entity type, document date range, correspondent, document type, Paperless tags, classification state, semantic completeness, person, organization, country, case, and relationship type filters.

Support list/grid toggle, stable pagination, and sorting by newest, oldest, date added, title, and correspondent. Explore should feel calm and browsable; it must not inherit the dense bulk-operation styling of Classify.

Use Paperless for Paperless metadata/OCR queries and AtlasDocs PostgreSQL for semantic filters. Do not add a vector database or second full-text index in this sprint.

Explore results are AtlasDocs entities with an internal UUID, human-readable label, entity type, safe display metadata, relationship summary, and authorized Paperless actions for Paperless-backed documents. Do not normally display raw UUIDs or Paperless IDs.

## Semantic layer improvements

### Entity type registry

Centralize entity display metadata: code, display label, icon or visual marker, searchable status, valid relationship-target status, and dedicated-page status.

Initial types: Document, Person, Organization, Country, Case, and Concept. Do not add empty NativeNote behavior merely for symmetry.

### Relationship constraints

Relationship types should declare valid source and target entity types for UI guidance. The backend remains authoritative.

```text
source-country -> Country
concerns       -> Person or Organization
replies-to     -> Document
belongs-to     -> Case
document-type  -> Concept
```

### Entity detail foundation

Add basic entity detail pages showing identity, type, relationships, related documents, provenance, status, and backlinks where available. Document detail remains richer because it includes preview and Paperless actions. Do not implement graph visualization yet.

### Semantic completeness

Expose explainable states such as empty, partial, classified, and needs review. Do not hardcode tax-specific rules; use relationship-type or configuration-driven rules.

## Relationship UX

Relationship targets must be AtlasDocs entities, never manually entered Paperless IDs.

```text
Add relationship -> choose target entity type -> choose relationship type
                 -> search AtlasDocs -> select entity -> save
```

Use autocomplete, valid target constraints, keyboard navigation, clear provenance, and progressive disclosure of technical details.

## API and architecture rules

- Preserve v0.5 API compatibility.
- Keep Paperless behind `PaperlessClient`.
- Never query Paperless PostgreSQL directly.
- Keep Atlas UUIDs separate from Paperless IDs.
- Keep relationships typed, directed/symmetric as configured, and N:N.
- Preserve provenance and status.
- Add migrations only when durable state requires them.
- Do not introduce graph databases, vector databases, or a new queue framework.

## Security

- Every Paperless-backed result must pass Paperless authorization.
- Inaccessible documents must not appear in Explore, counts, autocomplete, previews, downloads, or related-entity summaries.
- `PAPERLESS_BASE_URL` is server-side only.
- `PAPERLESS_PUBLIC_URL` is browser-facing only.
- Credentials and tokens must never reach browser code, URLs, logs, or raw errors.

## Implementation phases

### Phase A: document experience

Correct optional title propagation, preserve deterministic ingestion resolution, implement inline Preview, and validate Download and Paperless fallback actions.

### Phase B: semantic API foundation

Add the entity search result contract, Explore query contract, entity type registry, relationship target constraints, and semantic completeness calculation.

### Phase C: Explore UI

Add Explore navigation, search, filters, sorting, pagination, list/grid mode, document/entity result cards, and loading/empty/error/unauthorized states.

### Phase D: entity context

Add basic entity detail pages, related documents, relationships, provenance, and backlinks.

### Phase E: home and validation

Add the home launcher and task summaries, move maintenance actions out of primary navigation, and validate desktop/mobile, accessibility, and keyboard behavior.

## Testing

Backend tests must cover title supplied/omitted, deterministic resolution, task responses with/without IDs, Explore query composition, authorization filtering, entity constraints, completeness, pagination, and preview/download authorization.

Frontend and browser tests must cover inline preview, download, Paperless fallback, Explore list/grid, filters, entity navigation, relationship autocomplete, responsive layout, keyboard navigation, and all major loading/empty/error states.

End-to-end tests must cover upload with a title, upload without a title, READY state, preview, Explore discovery, entity detail, and authorization filtering.

## Explicitly deferred

Do not implement in v0.6: global graph visualization or graph editing, the full Perspectives system, a timeline engine, Evidence entities, LLMs, MCP, embeddings, vector search, Supernova workloads, a Paperless viewer replacement, or complex multi-user semantic ACLs.

These remain in `docs/semantic-navigation-spec.md` as future direction.

## Acceptance criteria

1. AtlasDocs never writes an internal UUID into a Paperless title when no title is supplied.
2. Supplied titles are preserved.
3. Preview opens inline and Download works through the authenticated BFF.
4. Paperless remains a secondary original-document action.
5. Explore is a separate primary navigation mode with search, filters, sorting, pagination, and list/grid display.
6. Explore returns AtlasDocs entities, not only raw documents.
7. Paperless-backed results respect authorization.
8. Relationship targets use AtlasDocs entity search and server-side type constraints.
9. Basic entity detail pages exist for current entity types.
10. Home distinguishes discovery from operational queues.
11. Reconcile and Disconnect are no longer primary navigation items.
12. No graph database, vector database, LLM, or direct Paperless database coupling is introduced.
13. Backend, frontend, browser, migration, and Docker tests pass.
14. Public AtlasDocs documentation describes the new product boundary and roadmap.

## Amendment: Document deletion and replacement

### A. Paperless-backed deletion

AtlasDocs must eventually allow users to delete a Paperless-backed document without opening Paperless separately.

The operation must use the authenticated user's supported Paperless API permissions:

```text
AtlasDocs request
  -> Paperless authorization
  -> Paperless deletion
  -> AtlasDocs semantic-state update
```

AtlasDocs must never bypass Paperless authorization. A user who cannot delete the Paperless document must not be able to delete it through AtlasDocs.

Deletion requires explicit confirmation. The confirmation must state that the original document will be deleted from Paperless and removed from normal AtlasDocs views. It must not expose raw Paperless IDs.

### B. Deleted-entity handling

AtlasDocs must not immediately reuse or repurpose the deleted entity UUID.

The data model should support a historical tombstone/deleted state so reconciliation and audit mechanisms can distinguish intentional deletion from an unavailable or broken reference.

Deleted or inaccessible documents must not expose metadata, relationships, counts, or search results through normal user queries.

### C. Same logical document: replacement

Replacement means a new physical representation of the same real-world document:

- corrected scan;
- better scan;
- replacement for a corrupted PDF;
- higher-quality representation;
- OCR-corrected representation of the same source.

The AtlasDocs entity UUID must remain unchanged. The Paperless external reference may change.

```text
Atlas entity 8f21c4...
  before: paperless:184
  after:  paperless:241
```

All AtlasDocs relationships remain attached to the same entity.

### D. Replacement workflow

Replacement must be failure-safe:

```text
Existing Atlas entity
  -> upload replacement through Paperless
  -> wait for successful ingestion
  -> resolve and validate new Paperless document
  -> switch Atlas external reference
  -> retire/delete old Paperless document
  -> preserve Atlas entity and relationships
```

The old Paperless document must not be deleted before the replacement is successfully ingested, resolved, authorized, and validated.

A failed replacement leaves the original backing document and Atlas semantic state unchanged.

Replacement should retain provenance including previous reference, new reference, timestamp, actor, reason when supplied, and previous/new checksums.

Replacement history describes external representations of one Atlas entity. It is not a document-to-document semantic relationship.

### E. New logical document: separate entity

Do not use replacement when a new real-world document exists.

Examples that require a new Atlas entity:

- revised tax assessment;
- amended contract;
- insurer response;
- follow-up medical report;
- corrected decision issued later by an authority.

These entities may be connected using typed N:N relationships such as `superseded-by`, `amended-by`, `answered-by`, or `follows-up`.

Decision rule:

```text
Another representation of the same real-world document -> REPLACE
New real-world document -> NEW ENTITY
```

### F. Identity invariant

```text
AtlasDocs UUID  = logical semantic identity
Paperless ID    = external backing representation
```

They must never be treated as interchangeable.

The future document UI should expose distinct actions:

```text
Preview | Download | Replace document | Delete document | Open in Paperless
```

Replacement preserves Atlas identity and relationships. Deletion is destructive and clearly communicated.

## Amendment: Semantic completeness at creation time

Semantic completeness is not only a viewer decoration. It is a lifecycle property evaluated when an entity is created or changed.

### Creation rules

- A newly created document entity starts with an explicit semantic state, normally `empty` or `partial`.
- Creation must validate the minimum identity contract: entity type, stable Atlas identity, and valid external reference when the entity is Paperless-backed.
- Optional relationships and metadata may be supplied during creation.
- The system must not require the user to invent a complete ontology before an uploaded document can exist.
- The UI should guide useful first classification without blocking safe ingestion.

### Completeness states

The state should be derived from configured relationship requirements or entity-type rules, not from tax-specific hardcoding:

```text
empty
  no confirmed semantic relationships

partial
  some useful semantics exist, but configured requirements are incomplete

classified
  configured minimum semantics are present

needs_review
  semantics exist but contain suggestions, conflicts, or unresolved review work
```

Creation, bulk assignment, relationship removal, replacement, and deletion must recalculate the state. The viewer displays the result, but does not own the calculation.

### Staged implementation

For v0.6, implement the completeness calculation and creation-time state assignment for the existing entity types. Keep the required rules small and explainable. Defer a full ontology-driven rules editor and domain-specific completeness models.
