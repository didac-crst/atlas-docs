# AtlasDocs v0.3 Roadmap — Entity + ExternalReference Core

## Status

Planning document that guided the v0.3 implementation. The schema migration plan
lives in `docs/v0.3-migration-plan.md`. Evidence, native notes, sidecars, LLMs,
MCP, embeddings, graph UI, migration tooling, and Supernova remain deferred.

## Goal

Generalize the Paperless-specific persistence model into the architecture’s
entity-first core **without breaking** the existing v0.1/v0.2 API and
classification workbench.

After v0.3:

```text
Paperless document 184
  -> ExternalReference(system=paperless, external_id=184)
  -> Entity (type=document, UUID)
  -> typed relationships (still exposed via /documents/184)
```

Paperless ids remain API convenience keys. They must not become AtlasDocs
primary keys.

## Why this milestone (and not a larger one)

The assessment shows the vertical slice works, but every later capability
(native notes, document↔document edges, inverses, sidecars, evidence) depends
on generic identity. Expanding features on `document_references.paperless_document_id`
and `target_concept_id` would deepen the wrong shape.

v0.3 is therefore a **foundation refactor with a compatibility facade**, not a
feature release for end users.

## In scope

### Persistence (conceptual; migration TBD after approval)

1. **Entity** remains the internal UUID identity; add an explicit **entity type**
   (at minimum `document`; prefer also representing seeded **concepts** as
   entities or documenting a transitional mapping if a full concept→entity move
   is too large for one milestone).
2. Replace Paperless-only `DocumentReference.paperless_document_id` with
   **`ExternalReference`**:
   - `entity_id`
   - `system` (e.g. `paperless`)
   - `external_id` (string form of the upstream id)
   - uniqueness on `(system, external_id)`
3. Keep a clear path from Paperless id → entity for all existing service and UI
   call sites.
4. Evolve **relationships** toward entity→entity edges (source entity, type,
   target entity) so N:N is not permanently concept-only.
5. Extend **relationship types** enough to record directionality intent:
   - directed vs symmetric flag, and/or
   - optional inverse type reference  
   Seed data may still only use directed document→concept-style types; the
   schema must not block inverses.
6. Preserve relationship **provenance** fields (`origin`, `status`,
   `created_at`). Align origin vocabulary with the architecture doc only if it
   can be done without breaking existing API clients (additive aliases or
   documented rename).
7. Avoid schema choices that force a single evidence document or make future
   `.atlas.json` sidecars impossible (stable entity UUIDs, exportable type codes,
   provenance on relationships).

### API compatibility

Must continue to work unchanged for callers:

- `GET /documents/{paperless_document_id}`
- `POST /documents/{paperless_document_id}/relationships`
- `GET /documents?unclassified=true&…`
- `DELETE /relationships/{id}`
- `GET /relationship-types`
- `GET /ontologies/{code}/concepts`
- UI routes under `/ui` keyed by Paperless id

Response bodies may **add** fields (e.g. `entity_id`) but must keep
`paperless_document_id`, relationship `type` / `target` / `origin` / `status`.

Internal resolution:

```text
paperless_document_id
  -> ExternalReference(system=paperless, external_id=str(id))
  -> Entity
```

### Explicit non-goals for the public product in v0.3

Do not introduce Satlas/Satellite/NAS/Cloudflare/Bitwarden/host-port assumptions.
Satlas remains on its current pinned image until a later public AtlasDocs image
is intentionally selected.

## Explicitly defer

| Deferred | Reason |
| --- | --- |
| Evidence | Architecture marks ~v1.0; preserve room only |
| Native notes | Needs content_owner + Markdown materialization milestone |
| LLMs | Derived knowledge policy not needed for identity refactor |
| MCP | Same |
| Embeddings | Unrelated to core identity |
| Graph visualization | UI novelty without entity graph maturity |
| Migration tooling (product CLI under `migration/`) | One-off Alembic for this change is enough later; no legacy import product |
| Supernova | Deployment/private concern |

Also defer: ontology editor, Person/Organization CRUD UX, brand-system redesign,
sidecar writer implementation, and any change that requires Satlas redeploy as
part of this PR series.

## Acceptance scenario (when implementation is approved)

1. Fresh database + migrations yield Entity + ExternalReference (or equivalent
   renamed tables) with no Paperless id as primary key.
2. Creating `source-country → Germany` for Paperless document `184` still works
   through the existing HTTP API.
3. Persisted document entity UUID ≠ `184`; lookup by
   `(paperless, "184")` external reference succeeds.
4. Duplicate relationship behavior remains deterministic and tested.
5. Authorization boundary unchanged: Paperless denial yields no semantic leak.
6. Classification workbench continues to function against the compatibility API.
7. No Evidence / NativeNote / LLM / MCP / sidecar writer / graph UI shipped.

## Implementation gate

After assessment approval, a follow-up implementation PR should include:

1. Concrete Alembic migration strategy (expand/contract or single cutover) and
   data backfill from `document_references`.
2. Model + service refactor behind the existing routes.
3. Updated seed loader if relationship-type metadata grows.
4. Automated tests for external-reference resolution and API compatibility.
5. Doc updates to README / ROADMAP status pointers.

Until that gate: **documentation only**.

## Suggested PR hygiene

- Architecture docs: this file + `docs/architecture-assessment.md` (this PR).
- Implementation: separate PR after approval.
- Satlas image pin bump: separate private deployment change, after a public
  release is chosen—never mixed with architecture or core refactors.
